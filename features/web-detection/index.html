Web Detection Test Pages

Each page shows one page problem, for trying web detection detectors by hand. A page marked control is a healthy twin of the page it names, and no detector should fire on it.

Detections panel. Every page has a square in the bottom-right corner that shows under the pointer: grey until a web event arrives, green after. Click it to open the panel:

  • Page measures: what the page itself measured, such as time to first byte, load end, first contentful paint, failed resources, broken images, input delay and long tasks.
  • Web events: each web event the browser sent for the page, with its data.
  • Breakage report: Collect report data shows what a breakage report sent now would hold, without sending one. A breakage report sent through the browser shows here too. Collecting runs the detectors that run on a breakage report, so a detector that fires an event on a report sends it.

Web events and report data need a build with the content-scope-scripts debug flag on. In other builds the panel waits. Add ?nooverlay to a page to leave the panel out.

Open the panel after the detectors under test have run. The open panel paints text and covers part of the viewport, which detectors of blank pages read.

The extension does not run on localhost. To use a local server (HOST=0.0.0.0 node server.js), open the pages by the machine's network address.

Slow or stuck loads

  • slow-load-10s: A render-blocking stylesheet answers after 10s: nothing paints and the load event ends at about 10s.
  • slow-load-5s control: A render-blocking stylesheet answers after 5s: nothing paints and the load event ends at about 5s.
  • slow-load-10s-painted control: Text paints at once, but one image answers after 10s, so the load event ends at about 10s.
  • load-never-ends: First paint at about 4s, and an embedded frame that never answers keeps the load event from ending.
  • slow-ttfb: The server takes 9s to answer the navigation request; the article then loads at once. Change delay (ms, up to 30000) to vary it.

Error pages

  • soft-404: A "404 Not Found" error page served with status 200, little visible text and a large inline bootstrap.
  • article-mentions-not-found control: A long, healthy article that mentions "page not found" once in its text and once inside a script string.
  • status-403: Default web server "403 Forbidden" page, served with status 403.
  • status-429: Default web server "429 Too Many Requests" page, served with status 429.
  • status-500: Default web server "500 Internal Server Error" page, served with status 500.
  • status-503: Default web server "503 Service Temporarily Unavailable" page, served with status 503.
  • forbidden-200: The same "403 Forbidden" page, served with status 200.
  • bare-forbidden-403: A "Forbidden" page without the 403 code in its text, served with status 403.
  • something-went-wrong: App error state: "Something went wrong" with a retry button and little else.

Block pages and challenges

  • waf-challenge: Firewall block page: one line of text and a script from a firewall resource path, served with status 403.
  • waf-error-status-long: Site-styled block page with full navigation and footer (over 2000 characters) plus the firewall script, served with status 403.
  • security-checkpoint: A security checkpoint interstitial that never clears.
  • security-checkpoint-cleared-late: A security checkpoint interstitial that clears after 9s and is replaced by the article.
  • bot-challenge: Bot-challenge interstitial with a spinner and a request reference, served with status 403.

Blank or empty pages

  • app-root-empty: Single-page app shell: empty #root, its bundle 404s and nothing renders; the title is set.
  • blank-no-title: Completely empty document: no title, empty body.
  • blank-then-late: Empty #app for 12s, then the article is rendered by script.
  • blank-viewport-region: A 60px header with navigation text renders, but the app container below it stays empty and fills the viewport (its bundle returns 500).
  • tiny-page: A document with a title and two characters of body text.
  • spinner-forever: App spinner that never resolves: its data request never answers and a second request returns 502.
  • skeleton-resolves-2s control: Skeleton placeholders in #app for 2s, then replaced by the article.

Broken resources

  • missing-styles: Three of four stylesheets fail (404, 404, 500); the page renders with fallback styling only.
  • missing-font: Two web fonts used by the visible text fail: one 404s, one returns bytes that do not decode.
  • broken-images: 6 of 10 content images fail (4 return a 404 HTML page, 2 return undecodable bytes), plus a broken 1x1 tracking pixel.
  • failed-subresources: Two scripts fail (503 and 404), a fetch returns 500, an XHR returns 404 and a beacon image 404s; the article itself renders.
  • blank-ad-slots: Article with collapsed ad slots: reserved empty boxes, empty about:blank frames, and hidden slots whose creatives fail.
  • comments-region-empty: Article whose comments widget script 404s, leaving the #comments container empty.
  • comments-region-filled control: Article whose #comments container holds three comments.

Overlays and walls

  • consent-fixed-undismissable: Full-viewport fixed consent overlay over the article, with buttons that do nothing and no close control.
  • consent-inline control: The same consent text in a normal (static) footer.
  • accept-or-pay-fixed: Full-viewport fixed "accept tracking or subscribe for €2.99" wall over the article.
  • accept-or-pay-inline control: The same accept-or-pay text in a static box at the end of the article.

Unresponsive pages

  • first-input-delay: Counts down for 3s, then blocks the main thread for 4s. A click during the block waits for it to end. freezeAt and freezeFor (ms) change the timing. Wait for the page to turn red, then click the button once.
  • long-tasks-after-load: After load the main thread is blocked from 2s to 6s, then by three 300ms tasks. Click "Show brew ratios" between 2s and 6s after load.

Healthy pages

  • healthy-article: Healthy article: all resources succeed and it loads in well under a second.
  • healthy-spa: Healthy single-page app: #root is filled by script within 300ms, and all resources succeed.
